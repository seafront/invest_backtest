# 매매 에이전트 설계

이 저장소의 데이터로 **AI 에이전트가 판단하고 주문까지 내는 프로그램**을 만든다면 어떤
구조여야 하는지 적어 둔다. 아직 구현된 것은 없다. 데이터 현황은
[`roadmap.md`](./roadmap.md)에, 프롬프트 원장은
[`book/ai_questions/`](./book/ai_questions/)에 있다.

> 실제 자금이 오가는 시스템이다. 아래의 검증 순서는 권고가 아니라 전제로 다룬다.

---

## 1. 데이터가 강제하는 제약

설계를 고르기 전에 먼저 닫히는 문이 셋 있다. 소스를 바꿔도 열리지 않는다.

### 1.1 일봉뿐이다

호가·체결·분봉이 없다. 만들 수 있는 것은 **종가 기준 일 1회 판단**뿐이다.

- 장중 대응, 자동 손절, 스캘핑 — 불가능
- 판단은 장 마감 후, 주문은 다음 거래일 시가 근처
- 그 사이의 갭이 그대로 슬리피지가 된다. 백테스트가 종가 체결을 가정한다면 **실전 성적은
  반드시 그보다 나쁘다**

### 1.2 데이터가 실시간이 아니다

일괄 수집을 주 1회 돌리면 에이전트는 최대 5거래일 지난 값으로 판단한다.
**매일 장 마감 후 자동 수집이 선행 조건이다.** 이것이 없으면 나머지 설계가 무의미하다.

### 1.3 LLM 전략은 백테스트가 오염된다

가장 중요하고 가장 자주 놓치는 항목이다.

2022년 삼성전자 데이터를 주고 "매수할까?"라고 물으면, 모델은 **그 뒤에 무슨 일이
있었는지 이미 알고 있다.** 학습 데이터에 들어 있기 때문이다. 백테스트 수익률이 좋게
나와도 그것은 전략이 좋아서가 아니라 미래를 알아서다.

따라서:

> **LLM이 매매 신호를 직접 내면 그 전략은 검증할 방법이 없다.**

이 한 줄이 아래 구조를 결정한다. 결정론적 계층과 LLM 계층을 분리하는 이유가 전부 여기 있다.

---

## 2. 구조 — 결정과 실행의 분리

```
① 데이터 수집       매일 장 마감 후 자동          (현재 저장소)
        ↓
② 결정론적 깔때기   728종목 → 15~30종목          ← 백테스트로 검증되는 유일한 계층
        ↓
③ LLM 판단          후보만 정성 검토, 구조화 출력  ← 전진 검증만 가능
        ↓
④ 리스크 게이트     코드로 강제 (프롬프트 아님)
        ↓
⑤ 주문 실행         KIS 모의 → 실전
        ↓
⑥ 기록·복기         모든 판단 근거를 저장
```

핵심 원칙은 하나다. **②와 ③을 섞지 않는다.** 섞는 순간 무엇이 성과를 냈는지 알 수 없게 되고,
그러면 고칠 수도 없다.

### ② 결정론적 깔때기 — 여기가 진짜 전략

`indicators.py` · `screener_scan.py` · `investor_flows` 로 만드는 규칙 기반 필터다.
**이 계층만이 백테스트로 검증된다.**

기존 `Strategy` 인터페이스를 그대로 쓰면 지금 엔진으로 바로 돌아간다.

```python
# services/strategies/base.py
@dataclass
class Signal:
    date: str
    action: str  # "BUY", "SELL", "HOLD"

class Strategy(ABC):
    def generate_signals(self, df, params) -> list[Signal]: ...
```

`questions.md` 33장이 이 계층의 사양서다. 제외 조건 → 재무 → 거래대금 → 수급 →
가격 위치 → 뉴스 → 단기/중기 → 위험 → 최종 분류의 9단계가 그대로 적혀 있다.

### ③ LLM 판단 — 좁게, 구조화해서

728종목 전부에 LLM을 돌리면 비싸고 느리다. **②가 걸러낸 20종목에만** 돌린다.
자유 서술이 아니라 스키마를 강제한다.

```python
class Proposal(BaseModel):
    ticker: str
    action: Literal["buy", "sell", "hold"]
    conviction: Literal["low", "medium", "high"]
    reasons: list[str]      # 각 항목이 실제 데이터를 인용할 것
    risks: list[str]
    invalidation: str       # "이 조건이 깨지면 판단을 철회한다"
```

`invalidation`이 중요하다. **판단이 틀렸다는 것을 무엇으로 알 수 있는지** 스스로 적게
만들면, 복기할 때 사후 합리화를 막을 수 있다. 이 필드가 없으면 모든 결과가 사후적으로
설명 가능해진다.

### ④ 리스크 게이트 — 반드시 코드로

프롬프트에 "손실 5% 넘으면 팔아"라고 쓰는 것과 코드로 막는 것은 다르다.
프롬프트는 무시될 수 있고, 모델을 바꾸면 동작도 바뀐다.

```python
HARD_LIMITS = {
    "max_position_pct": 10,     # 종목당 자산 대비
    "max_daily_orders": 3,
    "max_daily_loss_pct": 3,    # 넘으면 당일 매매 중단
    "min_avg_turnover": 1e9,    # 유동성 하한
    "blocklist": [...],         # 관리종목 등
}
```

여기에 둘이 더 붙어야 한다.

- **멱등성** — 같은 신호로 주문이 두 번 나가면 안 된다. 결정 ID를 주문에 실어 중복을 차단한다
- **킬 스위치** — 파일 하나로 전부 멈출 수 있어야 한다. 코드 수정이나 재배포가 필요하면 늦다

### ⑤ 실행 — 모의부터

`kis_client.py`에 환경 분리가 이미 들어 있다. 모의와 실전의 앱키를 각각 두고
`KIS_ENV`로 고르는 방식이라, 실전 키가 실수로 남을 여지가 적다.

```python
def _env() -> str:
    return "real" if os.getenv("KIS_ENV", "paper").lower() == "real" else "paper"
```

기본값이 `paper`인 것이 중요하다. **주문 엔드포인트는 아직 붙어 있지 않다.**
의도적으로 마지막에 붙인다.

### ⑥ 기록 — 나중이 아니라 처음부터

주문을 내기 훨씬 전부터 쌓아야 한다. ③계층은 백테스트가 안 되므로, **기록이 유일한
검증 수단이다.** 판단 시점의 입력값까지 함께 저장해야 나중에 재현할 수 있다.

## 3. LLM에게 맡길 것과 맡기면 안 되는 것

| 맡겨도 되는 것 | 맡기면 안 되는 것 |
|---|---|
| 상충하는 신호 해석 (수급은 좋은데 이격도 과열) | **가격 예측** |
| 여러 지표를 종합한 단계 분류 | 포지션 사이즈 결정 |
| 후보 종목 우선순위 | 손절 여부 판단 |
| 판단 근거 서술·복기 | 리스크 한도 해석 |
| 놓친 위험 요인 지적 | 최종 주문 여부 |

원칙: **LLM은 판단을 좁히고 설명하는 데 쓰고, 돈이 움직이는 결정은 코드가 한다.**

## 4. 검증 순서

건너뛸 수 있는 단계가 없다.

| 단계 | 최소 기간 | 통과 기준 |
|---|---|---|
| 1. ②계층 백테스트 | — | Buy & Hold 대비 우위, MDD가 감내 범위 |
| 2. 페이퍼 트레이딩 (기록만) | **3개월** | 실제 신호가 백테스트와 유사하게 나오는가 |
| 3. KIS 모의투자 | **3개월** | 슬리피지·체결 실패를 포함해도 유지되는가 |
| 4. 소액 실전 | 6개월 | 잃어도 되는 금액으로만 |
| 5. 확대 | — | |

2단계를 특히 줄이고 싶어지는데, 여기가 **③계층을 검증할 수 있는 유일한 구간**이다.
LLM 계층은 백테스트가 불가능하므로 전진 검증밖에 없고, 3개월은 최소치다.
그동안 판단과 결과를 전부 기록해야 ③이 실제로 기여했는지 사후에 판별할 수 있다.

## 5. 재사용할 것과 새로 만들 것

| 재사용 | 새로 만들 것 |
|---|---|
| `data_fetcher` · `bulk_job` — 수집 | 일 1회 스케줄러 (cron / APScheduler) |
| `indicators` · `market_stats` — 지표 | `agent/` — 제안 생성 |
| `investor_flow` · `fundamentals` | `risk/` — 하드 리밋 게이트 |
| `screener_scan` — 깔때기 | `execution/` — KIS 주문 + 멱등성 |
| `backtest_engine` — ②계층 검증 | `Decision` · `Order` · `Position` 테이블 |
| `kis_client` — 인증·유량·환경 분리 | 킬 스위치 |

### 저장소를 분리한다

이 저장소는 **연구·백테스트 도구**이고 매매 봇은 **운영 시스템**이라 요구되는 안정성이
다르다. 백테스트 화면을 고치다 주문 로직을 깨뜨리는 일은 없어야 한다.

이 저장소는 읽기 전용 데이터 API로 두고, 봇이 그것을 소비하는 형태가 깔끔하다.
공개 API의 제약과 라이선스 문제는 [`../README.md`](../README.md)의 API 개요를 참고한다.

## 6. 솔직한 한계

- 이 데이터로 만들 수 있는 것은 **일 1회 판단하는 스윙 전략**이다. 그 이상은 데이터가 없다
- **③계층이 수익에 기여하는지는 알 수 없다.** 백테스트로 증명할 수 없고, 전진 검증
  3~6개월로도 표본이 부족하다
- 슬리피지·거래비용·세금이 백테스트에 없다. 일봉 종가 체결 가정은 낙관적이다
- 728종목은 전 시장이 아니다. 지수 편입 종목만 있어 **생존 편향**이 있다

그래서 권하는 시작 방식:

> **먼저 ②계층만으로 봇을 만들어 모의투자를 돌리고, LLM은 "왜 이 종목을 골랐는지 설명"과
> "놓친 위험 지적"에만 쓴다.** ③계층이 주문 여부에 개입하는 것은 ②의 성적이 확인된 뒤다.

## 7. 첫 걸음

가장 저렴하면서 나머지 전부의 전제가 되는 것부터.

1. **매일 장 마감 후 자동 수집** — 이것이 없으면 나머지가 무의미하다
2. **`Decision` 테이블 + 페이퍼 트레이딩 기록** — 주문 없이 "오늘 무엇을 샀을 것인가"만 매일 저장
3. 2번이 3개월 쌓인 뒤에 ②계층 규칙을 다듬고, 그 다음에 모의투자

1·2번은 주문 코드가 전혀 없어 위험이 0인데, 나중에 반드시 필요한 데이터를 지금부터
쌓기 시작한다. 스냅샷과 같은 이유로 **늦게 시작할수록 손해다.**
